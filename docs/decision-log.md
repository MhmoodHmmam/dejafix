# Decision log

## R1: Project skeleton and Meko gateway (week 1)

- **Decision:** Django 5.2 LTS project. Meko is reached through our own async MCP gateway
  (`dejafix/meko/gateway.py`) built on the official `mcp` SDK, not through the model's MCP connector.
  - **Why:**
    - Meko identifies agents, conversations and datapacks by arguments, so code (not the model) must set them.
    - Calls are checked against the live schemas before sending, because Meko Cloud rejects unknown arguments.
    - Every call gets a timeout. Only read-only tools are retried, with backoff, so a timeout can't store the same memory twice.
    - Each call is recorded without its arguments, for our traces (A09).
- **Decision:** Build against the live tool schemas, saved by `manage.py meko_probe`, instead of the published docs.
  - **Why:** Meko Cloud publishes 57 tools. The docs miss several (`track_token_usage`, `selflearning_*`, `amp_*`).
  - Meko Cloud also requires `conversation_id` on calls whose schema marks it optional (for example, `datapack_list` answered with the in-band error `conversation_id_required`).
  - `conversation_create` requires a `datapack_id`, so the first datapack must be created in the portal.
- **Decision:** Secrets only from the environment (a stdlib `.env` loader, no new dependency).
  - `DEBUG` is off by default. `MekoConfig` hides the key from `repr`.
  - Plain HTTP is allowed only for a localhost Meko (A02, A04).
- **Rejected:**
  - The Anthropic MCP connector: the model would choose `agent_id`, and we'd lose per-call timeouts and records.
  - LangChain/Pydantic AI adapters: extra dependencies we don't need.
  - Self-hosting Meko: the README says Windows is not supported.
  - Django 6.x: 5.2 is the LTS release and supports Python 3.14.
- **Sources:**
  - [source] `mcp` 2.3.0 installed:
    - `mcp/client/client.py`: `Client`, `call_tool`, `list_tools(cursor=)`
    - `mcp/client/streamable_http.py`: `streamable_http_client(url, http_client=)`
    - `mcp_types/_types.py`: `CallToolResult.content`, `structured_content`, `is_error`; `ListToolsResult.next_cursor`
    - `mcp/server/mcpserver/server.py`: `MCPServer.tool`, used for the in-process test fake
  - [source] `httpx2` 2.16.2 installed: `HTTPStatusError(..., request=, response=)`, `AsyncClient`, `Timeout`
  - [read] Live Meko Cloud `tools/list` (saved to `docs/meko-tools.json`) and its in-band errors `conversation_id_required` and `datapack_id_required`
  - [read] github.com/yugabyte/meko `src/meko/docs/api.md`:
    - reply conventions: JSON as text, in-band `{"error","detail"}` with `isError: false`
    - Cloud rejects unknown arguments
  - [read] mekodata.ai/langchain and mekodata.ai/pydantic-ai: `Authorization: Bearer <api-key>` on `https://mcp.mekodata.ai/mcp`

## R2: Support agents, synthetic data and human review (week 2)

- **Decision:** A code-driven workflow (triage → retrieve → resolve → review), not a free agent.
  - Each agent is one Claude call with a Pydantic-typed output and **no tools**, so ticket text has nothing to act on.
  - Code runs the Meko calls in a fixed order, so "search before solving" can't be skipped.
  - The fixed order also keeps the benchmark repeatable.
- **Decision:** One Meko conversation per (ticket, agent).
  - Why: live schema says "Conversations are scoped per agent" and `conversation_add_message` needs the same `agent_id`.
  - All of a ticket's conversations share `run_id = dejafix:<ticket>`.
  - A fixed `session_id` and message `seed` make re-runs reconnect instead of duplicating.
- **Decision:** Retrieval uses `context_search` plus `knowledgebase_search`.
  - **Why:** live spike: a promoted memory disappears from memory search and comes back from `knowledgebase_search` (rerank 0.97 on a paraphrase). `context_search` did not return it, even with `force_source="knowledge_base"`.
- **Decision:** Only fixes promoted by the curator agent, in our exact text format, are trusted for reuse.
  - Corrections count only in their exact format.
  - **Why:**
    - Promotion is one-way: a test chunk from the spike could not be deleted.
    - Meko Cloud **auto-extracts memories from every conversation turn** under our agents' ids. A live run created 20 such memories, including unreviewed fixes. None contained the injection text.
- **Decision:** Memory is written only after a human decides.
  - Approval: the curator stores the fix and promotes it (collective memory).
  - Rejection: the reviewer's note is stored as a private learning, which resolvers see next time.
  - Approve/reject claim the row with a conditional `UPDATE` (no double promotion). The claim is released if Meko fails.
- **Decision:** Effort `low` for triage, reuse check and review; `medium` for solving. Server-side refusal fallback (`fallbacks="default"`) is on.
- **Live check (5 tickets + 1 approval, real Claude Opus 5.5 and Meko Cloud):**
  - T001 (new): 5,291 tokens, 13.1 s of model time.
  - Repeats T013, T025, T033 reused the approved fix:
    - 2,667 to 2,782 tokens each, about 49% fewer than T001.
    - 8.6 to 9.8 s of model time.
  - Cross-agent: T025 was handled by resolver-b. Cross-language: T033 is in Arabic.
  - Reuse scores were 0.994 to 1.0.
  - T013's reply adapted the approved fix to a bank holiday.
  - T017 (prompt injection) was escalated by the code rule; no memory was written.
- **Bug found by the live run:** the reviewer escalated a correct fix because it saw only policy passages, not the documentation the resolver used.
  - Fixed: the reviewer now gets the resolver's evidence.
  - Regression test: `test_reviewer_sees_the_documentation_the_resolver_relied_on`.
- **Rejected:**
  - Managed Agents / a tool-using agent: harder to enforce ordering and to benchmark, and a larger injection surface.
  - Trusting `context_search` alone: it misses promoted fixes.
  - Writing memory on every resolution: unreviewed fixes would be reused.

## R3: Self-learning loop and case files (week 3)

- **Decision:** Close knowledge gaps with Meko's own self-learning tools, with a human in the loop.
  - The loop: `find_gaps` → `draft_gap_articles` → a human publishes in the admin → `verify_gaps`.
  - `find_gaps` reads `selflearning_status`, then `selflearning_shortfalls(add_context)`, then `selflearning_query_log` for each search.
    - Shortfall rows don't name the agent, so the log entry is needed to keep only our resolvers' searches. The spike agent's searches are ignored.
    - The log entry also names the conversation, which links each gap to its ticket.
  - The librarian (`dejafix-librarian`, effort `low`, no tools) drafts only from human-approved resolutions plus documentation.
    - Without an approved fix, the gap becomes `needs_author` without calling Claude.
  - Publishing uploads a markdown document to the knowledge base.
    - **Why a document and not a memory:** `context_search` (which Meko grades) reads knowledge-base documents but not promoted memories.
    - The knowledge base is trusted context for every resolver, so only a human publishes.
  - `verify_gaps` replays the search with `selflearning_verify`.
    - The "before" values are frozen at publish time.
    - Replays are capped at 10 per run, the same as Meko's limit per minute.
- **Decision:** A case file (JSON) is stored as a Meko artifact (`artifact_put`) on every human decision. The shared memory links to it with a `Case file: <sha256>` line.
  - It holds no ticket text, customer or reviewer name.
  - It has no timestamps, so a retry produces the same bytes and Meko stores it once.
  - The case file is written before the memory, and a failure releases the review claim.
- **Live findings:**
  - Gaps were imported: card_closed refund (T017), bank holiday (T013) and weekend (T001).
    - T017 was escalated, so it has no approved fix and became `needs_author`.
    - Two drafts were made for 4,009 tokens. Before publishing, I checked them line by line against `payouts.md` and the approved T001 fix: nothing was invented.
  - Replays:
    - Bank holiday: mid 0.68 → high 0.78.
    - Weekend: mid 0.69 → high 0.87.
    - Meko's Self-learning tab marks both searches `verified`.
  - **Attribution caveat:** the replay grades every source. Its top 5 hits were past *conversations*, including our own trace turns, which hold the search text.
    - Part of the jump comes from history that piled up after the first search, not from the article.
    - So `verify_gaps` now records the replay's top source (`source_after`) and the article's own knowledge-base rank (`kb_rank_after`).
    - Live, both articles rank #1 in the knowledge base for their search, above the original payouts doc.
    - A KB-only `context_search` graded the weekend query `high` and the holiday query `mid`.
  - **Bug found by the live run:** `conversation_create` returns 32 hex digits, but the search log writes the same id as a UUID with hyphens, so no gap was linked to its ticket.
    - Fixed by normalizing both sides in the query (`Lower(Replace(...))`).
    - Regression test: `test_links_the_ticket_when_the_log_writes_the_conversation_id_as_a_uuid`.
- **Rejected:**
  - `memory_add` to close gaps: `context_search` does not grade promoted memories.
  - Publishing drafts without a human: it would poison trusted context.
  - Trusting Meko's replay band alone: it counts our own traces (see the caveat above).
- **Sources:**
  - [read] Live schemas: `selflearning_status`, `_shortfalls`, `_query_log`, `_verify` (owner role, 10 replays a minute, counts against search quota), `artifact_put` / `artifact_get` (idempotent, < 1 MB inline), `knowledgebase_upload_document` ("passages come back from knowledgebase_search and context_search").
  - [read] Live replies: status (quality 25%, `add_context` with 9 searches), shortfalls, a full query-log entry (`agent_id`, `conversation_id`, `source_outcomes`), and a verify reply (`before` / `after` / `outcome` / `top_results[].s`).
  - [source] Django 5.2.19 installed:
    - `CheckConstraint(condition=...)` in `db/models/constraints.py`
    - `Replace` and `Lower` in `db/models/functions/text.py`
    - `ModelAdmin.get_readonly_fields` and action `allowed_permissions` in `contrib/admin/options.py`
  - [knowledge] OWASP Top 10:2025:
    - A01: publish and dismiss are staff actions with change permission.
    - A05: weak-search text is escaped in `<weak_search>`.
    - A06: human gate before the knowledge base; conditional-update claims for publish and verify.
    - A08: the presigned upload is HTTPS only.
    - A09: no personal data in case files or logs.

## R4: Benchmark with and without shared memory (week 4)

- **Decision:** Two arms over all 36 tickets, in ticket order, with the same agents, prompts, effort and documentation.
  - Each arm runs in its own new datapack, created with `datapack_create` and seeded with the same 9 docs.
  - The only difference is memory. The docs-only arm runs the same Meko searches but keeps only documentation passages.
  - Each run trusts only its own curator and reviewer identities. Ticket refs are prefixed with the run name, so traces never collide.
- **Decision:** Deterministic grading against ground-truth keywords per issue (`data/tickets.json`), not an LLM judge.
  - A fix is correct only if it mentions every keyword and was not escalated.
  - The two injection tickets are flagged in the ground truth and must be escalated with nothing stored.
  - The rules were fixed before the run and not changed after seeing results, even where they are strict (T003: "use a live key" without the `lp_live_` prefix counts as wrong).
- **Decision:** A simulated reviewer in the Meko arm decides each new fix right away.
  - It approves complete fixes. It rejects incomplete ones with a note naming the missing keywords.
  - Its notes come from the ground truth, so it is kinder than a busy human. The report says so.
- **Results** (one run per arm, `claude-opus-5-5`; full table in `docs/benchmark.md`):
  - Correct: docs-only 25/36, Meko 30/36. First occurrences 8/12 in both; repeats 17/24 vs 22/24.
  - Tokens on repeats: 5,348 vs 3,537 on average (-34%). Total: 192,558 vs 148,998 tokens ($1.43 vs $1.11 at list price).
  - Human touches: 36/36 vs 19/36 (17 repeats reused an approved fix).
  - False reuse 0. Both injection tickets escalated with nothing stored, in both arms.
  - Learning from corrections: T002, T003 and T010 were rejected with notes, and their repeats T014, T015 and T023 were correct in the Meko arm but wrong in the docs-only arm.
  - The reuse check works as a gate: T036 was offered T012's fix at score 1.0, judged a different cause, and solved correctly from the docs.
- **Calibration:** every threshold from 0.50 to 0.90 gave precision 1.00 and recall 1.00. No other issue's fix was ever offered, so the data cannot test how low the threshold can safely go. `REUSE_MIN_RERANK_SCORE` stays at 0.80.
  - The first report said "Recommended: 0.5". That falsely precise value was replaced by the tied range, with an explicit caveat.
- **Bugs found while building the benchmark:**
  - **Security:** an injection ticket matching an approved fix took the reuse path, which skips review, so the "instructions in the ticket → escalate" rule never ran and the ticket closed with a model-written reply. Fixed: injection tickets never take the reuse path. Regression test: `test_injection_ticket_is_escalated_even_when_an_approved_fix_matches`.
  - **Security:** human corrections were trusted by their text format alone, from any agent (memory search spans every agent). Fixed: only the reviewer agent's corrections count; live `context_search` memory hits carry `agent_id`. Regression test: `test_correction_written_by_an_untrusted_agent_is_ignored`.
- **Limits:** one run per arm (no repeated runs, so no confidence intervals); 36 synthetic tickets; a lenient simulated reviewer.
- **Rejected:**
  - Running both arms in the demo datapack: it already holds a promoted fix and two articles, and `knowledgebase_search` keeps only the top 8 hits.
  - An LLM judge: costlier, and harder to repeat than keyword grading.
- **Sources:**
  - [read] Claude API skill, model table (cached 2026-11-03): `claude-opus-5-5` at $4 / $20 per million input / output tokens.
  - [read] Live schemas: `datapack_create` (`name` must be unique across the platform; `datapack_id` is for trace routing only), `datapack_delete` (irreversible, not used).
  - [read] A live `context_search` memory hit: keys include `agent_id`, `score` and `memory`.
  - [source] Django 5.2.19: `UniqueConstraint(fields=..., name=...)` and `CheckConstraint(condition=...)` in `db/models/constraints.py`.
  - [knowledge] OWASP Top 10:2025:
    - A01: benchmark admin screens are staff-only and read-only.
    - A06: injection tickets always reach a human; only trusted agents' memories steer resolvers.

## R5: Staff dashboard and review pages (week 5)

- **Decision:** Server-rendered Django pages, one CSS file, and bar charts drawn as SVG on the server. No JavaScript at all.
  - Pages:
    - dashboard;
    - ticket list and ticket page with the full agent trace;
    - Approve, Reject (with a note) and Run the agents;
    - knowledge gaps: edit, publish, dismiss;
    - benchmark.
  - Views stay thin: forms validate, and `support.services` / `support.gaps` do the work.
  - The Django admin stays as a fallback.
- **Decision:** A strict Content-Security-Policy (`script-src 'none'`, `style-src 'self'`, `frame-ancestors 'none'`, `form-action 'self'`) from our own middleware.
  - Django 5.2 has no CSP middleware: `django/middleware/` holds none.
  - `/admin/` is exempt because it relies on inline scripts.
- **Decision:** Status codes on the HTML actions.
  - A state conflict (reviewed twice, publishing twice, editing a published article) renders the page with **409**.
  - A Meko or Claude failure renders it with **502**, and the state is unchanged.
  - Invalid input gets **400** with field errors.
  - Success redirects (POST/Redirect/GET).
- **Decision:** Meko's context quality on the dashboard comes from a live `selflearning_status` call.
  - It has a 5 s timeout and is cached under one shared key: 300 s after a success, 60 s after a failure. The value is datapack-wide, not per user.
  - A failure shows "unavailable".
- **Access:** every page is staff-only (anonymous users go to the login page, other users get 403). Each action also needs the model's change permission. POST only, with CSRF.
- **Performance:** the dashboard runs 7 queries, plus 2 per benchmark run shown, and the count does not grow with the data. The ticket list runs 4 queries for a page of 50.
- **Live check** (local server, built-in browser, real Claude and Meko):
  - I logged in as a local test staff user. Its random password is in the git-ignored `var/demo-login.txt`.
  - The dashboard showed Meko context quality at 27%.
  - Run the agents on T002 took 5,779 tokens and 17.4 s of model time; the ticket is now awaiting review. It was not approved, so nothing was promoted.
  - At 375 px wide nothing overflows horizontally, and the console showed no CSP violations.
  - Fix from that check: step names such as `reuse_check` now display as "Reuse check".
- **Rejected:**
  - React or HTMX plus a chart library: new dependencies for pages that don't need client code.
  - Running the agents in a background queue (Celery or RQ): a new dependency. For a local demo a synchronous request is enough, and the README says so.
- **Sources:**
  - [source] Django 5.2.19 installed:
    - `contrib/auth/decorators.py`: `login_required`, `permission_required(raise_exception=)`
    - `views/decorators/http.py`: `require_POST`, `require_GET`
    - `core/paginator.py`: `Paginator.page`, which raises `EmptyPage` / `PageNotAnInteger`
    - `contrib/auth/views.py`: `LoginView`; `LogoutView` accepts only POST
    - no CSP module in `django/middleware/`
  - [knowledge] MDN, Content-Security-Policy directives.
  - [knowledge] OWASP Top 10:2025:
    - A01: staff-only pages and per-action permissions
    - A02: strict CSP; `DEBUG` off
    - A05: templates auto-escape customer text, checked by a test with `<script>`
    - A08: CSRF on every POST; forms list their fields explicitly

## R7: public repository and the app's database on Meko Postgres (week 7)

- **Data move:**
  - `dumpdata` (without content types, permissions, sessions and admin log), then `migrate` and `loaddata` on Postgres: 146 objects.
  - The row count of every model matches SQLite, and every ID sequence is past its table's maximum ID.
- **New dependency:** `psycopg[binary]==3.3.8`, released 2026-11-04, with a binary wheel for Python 3.14 on Windows. Django 5.2 needs psycopg 3.1.8 or newer.
- **Live checks on the cluster:**
  - The full suite passed on Postgres: 184 tests in 668 s.
  - The staff pages showed the moved data correctly. Load times: dashboard about 1.9 s, ticket pages about 1.0 s, gaps 0.7 s. Each query is a network round trip.
- **Fix found during the checks:**
  - With Postgres in `.env`, a plain `manage.py test` went to the network and took 11 minutes, which broke the README's "tests never touch the network".

  - The interrupted run left `test_dejafix` on the cluster, and I dropped it.

  - Letting Meko generate the password: it comes back once in the tool reply, so it would pass through the output. Ours went straight to `.env`.
  - Opening the endpoint to a range of addresses: Meko refuses anything wider than /24, and one /32 is the least exposure.

## R8: reproducible Meko Postgres, CI and a faster dashboard (week 8)
- **Decision, `manage.py provision_db`:**
  - Week 7 created the cluster with one-off scripts, so nobody else could repeat it. The command does it from the repo as agent `dejafix-dba`, in one deduplicated Meko conversation.
  - First run (`--allow-cidr` required): `amp_core_budget` (stop if under 0.5 vCPU is free), `amp_cluster_list` (stop if the name exists), `amp_cluster_create`, then `amp_compute_list` for the endpoint.

## R14: agents in the background with real progress, and login throttling (week 14)
- **Decision, claim:** a new ticket status `running` ("Agents working"), set by one conditional UPDATE (`claim_ticket`). Only new, failed or stale-running tickets can be claimed, so a second start gets 409.
  - A run is stale after 5 minutes (`Ticket.STALE_RUN_AFTER`, from `updated_at`), for when the server stops mid-run.
  - On failure only this run's claim is released (`status=running` → `failed`). The outcome is saved only while the claim is held.
  - This replaces the week 12 conditional on new/failed and closes that race at its root.
  - The migration only changes the status choices.
- **Decision, background run:** the view claims and returns at once. A two-thread `ThreadPoolExecutor` runs the agents after the claim commits (`transaction.on_commit`).
  - The thread fails closed: a crash is logged and the claim released.
  - It gives its database connection back with `close_old_connections()`.
  - Tests and management commands run inline (`DEJAFIX_RUN_AGENTS_INLINE`, on by default under `manage.py test`), so every existing test kept its synchronous flow unchanged.
- **Decision, progress:**
  - `run_pipeline` gets an optional `on_step` callback, fired as each step is recorded (a list subclass, so all five step sites report without changes).
  - The service stores the step name, agent, tokens, model time and Meko calls in the cache, never ticket text.
  - `/tickets/<ref>/progress/` (staff, GET, `no-store`) returns them with the status. `app.js` polls it every second and reloads when the run is done. Without JavaScript, a `<noscript>` meta refresh reloads every 5 seconds.
  - Nothing partial is stored in the database: a failed run still leaves no agent steps, as the existing test requires.
- **Decision, login:** `ThrottledLoginView` answers 429 after 5 failed attempts for one username from one address within 15 minutes, even with the right password.
  - The same message is shown whether or not the user exists. A success clears the count.
  - The address is `REMOTE_ADDR`, because `X-Forwarded-For` can be set by anyone. Cache keys are SHA-256 hashes, not raw usernames.
- **Live check:** T005 was run from the real UI in background mode. The page showed "Agents working", a running clock and Triage's real numbers (1,047 tokens, 3 Meko calls) 12.7 s after the click. It reloaded into "Awaiting human review" at 39 s.
- **Rejected:**
  - Celery or a similar task queue: new dependencies and another service to run.
  - A worker command reading a job table: a second process for the demo.
  - Writing agent steps to the database as they finish: it would change the "nothing stored after a failure" rule that a test and the case files rely on.
- **Limits** (documented in the README):
  - The pool, the progress and the login counters live in the web process. Several processes need a worker and a shared cache.
  - A server restart mid-run frees the ticket after 5 minutes.

  - A promoted fix comes back from `knowledgebase_search` with a `document_id` and `metadata_filters.memory_id`.
  - `memory_update` and `memory_delete_by_id` on it answer `memory_is_promoted`: "Promoted memories are not yet mutable through MCP (GH #314)". Meko points to its Cloud UI's Learnings tab instead.
  - `knowledgebase_delete_document` with the hit's `document_id` answers `NOT_FOUND`, and the fix keeps coming back.
  - So the plan's fallback was used, and no new Meko tool was added (still 23).
- **Decision, retirement:**
  - `POST /memory/<memory_id>/retire/` (staff with the change-resolution permission, a reason required, keys required) calls `services.retire_fix`.
  - A conditional UPDATE claims it, so a second retirement gets 409. On a Meko failure the claim is released and the page answers 502.
  - In Meko (`pipeline.retire_shared_fix`), as `dejafix-human-review`: a case file (`dejafix-case-<ref>-retired.json`, with the retired memory ID and the tickets that reused it), the reason as a human correction (the existing format, so resolvers and the reviewer already read it), and a traced `retire_fix` turn.
  - New fields on `Resolution` (`retired_at`, `retired_by`, `retirement_note`, `retirement_case_file_hash`). A check constraint allows retiring only an approved fix with a promoted memory.
- **Decision, retrieval:** `retrieve()` and `run_pipeline()` take `retired_fix_ids`. The service passes the retired IDs on every run, and a skipped fix is listed in the retrieve step (`retired_fixes_skipped`). The benchmark passes none, because its datapacks are separate.
- **Decision, pages:**
  - The shared-memory page lists retired fixes apart, with the reason. The page still uses the same 6 queries.
  - The corrections count includes retirement reasons.
  - A ticket that reused a retired fix shows "Reused a retired fix: check this reply" with the reason.
- **Live check** (real Claude and Meko, the throwaway datapack, a throwaway SQLite copy):
  - T007 was approved, and T019 reused its fix (score 0.997).
  - The fix was retired with a reason, answering 302 with a case file stored.
  - T020 (same issue) then skipped the retired fix, read 1 learning, and its fix applied the reason (`corrections_applied` names the new export path). It used 6,429 tokens and went to human review.
  - The pages were checked in light, dark and at phone width.
- **Rejected:**
  - Editing the fix in place: Meko refuses it for promoted memories, and a fix approved by a person shouldn't change under them.
  - Re-running the affected tickets automatically: a closed reply was already sent to a customer, so a person decides.
- **Limits:**
  - The retired fix stays in Meko's knowledge base until Meko allows it to be deleted. Another app reading the same datapack would still see it.
  - A run that already started before a retirement can still reuse the fix. That ticket then shows the retired-fix warning.

## R18: the drift benchmark, an approved fix after a product change (week 19)
- **Question:** a reused fix skips human review. When the product changes, does an outdated fix keep being reused, and does retiring it help?
- **Decision, cases** (`data/drift.json`):
  - Three issues, each with:
    - a first ticket from `data/tickets.json` (T001, T002, T006);
    - two existing repeats;
    - a product update (`data/drift/updates/`, plus the invoice update from week 18);
    - new keywords that name what changed;
    - the reason a staff member would write.
  - `load_drift` refuses unknown tickets, tickets of another issue, a first ticket that is not the issue's first occurrence, new keywords that change nothing, and an empty reason.
- **Decision, run** (`manage.py drift_benchmark run <name> --arm stale|retire`): every run uses a fresh datapack with `data/kb`.
  1. The first tickets are solved and approved by the main benchmark's simulated reviewer, graded by the old keywords.
  2. The updates are uploaded (`seed_knowledge --file`, new).
  3. In the retire arm, `retire_shared_fix` runs with each reason.
  4. The repeats run, graded by the new keywords, and a new fix is reviewed as usual.
  - Results go to `docs/drift.json`, not the app's tables, so the main benchmark and `/benchmark/` are untouched.
  - The datapack and document helpers were factored out of `support/benchmark.py` (`new_datapack`, `count_documents`) and reused.
- **Live result:**
  - S1 (stale): 0/6 correct after the change, and 5/6 reused the outdated fix. The update was in the knowledge base all along.
  - R1 (retire): 6/6 correct and 0 reused it. Every repeat skipped the retired fix, and T026 reused the fix newly approved on T014.
  - Retiring costs tokens: 6,387 against 3,362 per repeat, and 5 of 6 repeats needed a person, because new fixes are reviewed.
- **Found live, Meko's free-tier limits:**
  - During S2, Meko answered `free_tier_limit_reached` ("Limit of 1000 lifetime requests for 'conversation_add_message'"). Then R2 could not create a datapack (`FREE_TIER_DATAPACK_LIMIT`).
  - Decision: a run with failed tickets is left out of the comparison and named with its first error ("Runs left out"), because outside failures would count as wrong answers. The report's limits line counts complete runs instead of assuming two per arm.
  - Consequence: until the Meko account has a higher plan, no new agent run works on it, because every step is a traced turn. The recorded demo (`load_demo`) is unaffected.
- **Rejected:**
  - Storing drift results as `BenchmarkRun` rows: different arms and grading would mix into the main report.
  - Making trace turns best-effort to get past the quota: traces are part of what the app shows and stores.
- **Tests:** +11 (`support/tests/test_drift.py`), 300 in all:

  - a failed ticket that doesn't stop the run;
